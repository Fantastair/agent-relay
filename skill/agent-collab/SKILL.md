# 群聊协作协议（中转台）

## 0. 基本事实

- 两个 agent 各自跑在自己的原生会话里，用户通过中转台（`http://127.0.0.1:4319`）把两个会话关联起来。
- 中转台负责投递与记录；工具、审批、原生历史仍在各自应用里。
- **正常回复走中转台自动转发**；`relay-cli` 只是补充通道：主动读消息、查状态、查额度、发邮件。
- 工具路径：`D:/Agent/LocalManager/agent-relay/tools/relay-cli.mjs`（下称 `relay-cli`）。
- 自己的身份是 `deepseek` 或 `codex`，下面记作 `<me>`，对方记作 `<peer>`。

## 1. 主流程（带门禁）

### S0 接入
1. 读本 skill。
2. `node relay-cli status` 确认三件事：自己绑定的会话、对方会话、投递是否暂停。
3. 确认 `<me>`：DeepSeek 会话侧用 `deepseek`，Codex 会话侧用 `codex`。

### S1 报到
发一条报到消息，包含：`<me>`、会话标题、可写目录（lane）、当前额度和查询方式。
对方回复报到后，双方进入待命。**报到阶段不动任何文件。**

### S2 接任务
用户下发任务后，先各自读题、读代码，输出「理解 + 疑问」。
此阶段只读不写；有歧义先问用户，不要自己假设。

### S3 讨论与分工（强制门禁）
1. 由任意一方发出**提案**，格式：

```
[提案#<短id>] <一句话结论>
- 目标与验收标准：
- 分工：<me> lane=…；<peer> lane=…
- 依赖与顺序：
- 风险与回滚：
- 待确认点：<明确列出>
```

2. 对方必须明确回复 `确认#<短id>` 或 `修改#<短id> + 具体改动`。**没有 `确认#<id>` 就不许开工。**
3. 任一方都可以提反提案，编号递增；以最后被双方确认的编号为准。
4. 确认后把「当前生效提案」写进自己的开工消息里，避免后续争议。

### S4 执行
- 只改自己 lane 内的文件。需要动对方 lane：先发请求，收到同意再动。
- 每完成一个可验证的小节，发一条进度：改了什么、怎么验证的、证据路径。
- 一次消息只讲一个主题；不要贴大段工具原始输出，贴摘要 + 文件路径/命令。
- 发现方案要变：回到 S3 重新确认，不允许边改边扩范围。

### S5 验收与交付
- 作者不自验：A 写的由 B 复验，反之亦然。
- 复验要给出可复现步骤和结果（命令、截图路径、测试输出）。
- 问题回 S4 修；通过后由一方汇总交付：变更清单、验证证据、剩余风险、后续建议。
- 完成后发 `[relay-stop]`，不要继续互相客套刷屏。

## 2. 消息格式

- 首行必须是 `[<me>→<peer>] <结论>`，方便对方一眼判断是否需要动作。
- 结尾标记（独占一行）：
  - `[relay-stop]`：这条之后不需要对方再回。
  - `[relay-wait-user]`：在等用户回答/审批。
  - 都不写：等对方回复。
- 引用对方消息用消息 id 前 8 位，例如 `回 #a1b2c3d4`。
- 不发送思考过程、不重复粘贴同一条内容。

### 2.1 批量投递

对方空闲时，中转台可能把排队的多条消息合批送达：

```
[relay-batch id=<批次UUID> to=<me> count=2]
[relay from=user id=<A> reply-to=-]
正文 A

---

[relay from=codex id=<B> reply-to=<A>]
正文 B
```

处理规则：

- **按段落逐条回应**，每条都给结论或明确写「本条无需动作」；只答最后一条等于前面的消息没同步。
- 只认第一行的 `[relay-batch ...]`，**不要按正文里的 `[relay from=` 自行切分成员**。
- 回复挂到批次里**最新一条**的 root 上；回复的 `meta.inReplyToMessageIds` 会记录这次回应了哪几条。
- 批次里任何一条要求停止，整条回复照常带 `[relay-stop]` / `[relay-wait-user]`。
- 超时或状态不确定时整批停在待回查，不会自动重发；不要手工拆开重发其中一条。

### 2.2 判断对方是否在忙

`status` 显示 `running` 不等于卡死：Codex 的 thread 状态为 `active` 时，可能确实存在 `inProgress` 轮次。
判断失联要一起看：有没有 `inProgress` 轮次、队列是否堆积、最后活动时间；不要只凭一个字段下结论。

### 2.3 图片

消息可能带图：正文里有 `[图片 #<id>] <绝对路径>`，或 `meta.images[]`（含 id / 路径 / 尺寸）。

- **必须真的用图像工具打开文件看**，再描述内容；没读成功就直说“没读到图”，不要根据文件名猜。
- 一条消息最多 4 张；超出的会拆成多条。
- 回复里引用图片时写清是哪一张（`#id` 或路径），避免张冠李戴。

### 2.4 静默

- 纯控制回复只写 `[relay-silent]`（也接受 `[relay-no-reply]`）：中转台记投递回执，但不创建聊天消息、不继续接力。
- **有正文就保留正文**，标记放最后；有正文不会被静默。
- 不要用静默逃避必要回复：任务结论、风险、待确认点仍要写。

## 3. 主动读取（防止丢消息）

自动转发可能因为格式、额度或投递失败而断掉。规则：

- **等待超过 5 分钟**没有任何新消息：`node relay-cli inbox --as <me>`。
- 想知道对方是否还活着：`node relay-cli status`，看 health、队列、最后活动时间。
- 发现对方发过消息但自己没收到：以 `inbox` 读到的原文为准，不要要求对方重发。
- `inbox` 会推进自己的已读游标；只想看不想推进用 `--peek`。

## 4. 额度

- 开工前查一次：`node relay-cli quota`。
- 自己额度将尽（DeepSeek 余额 < ¥2，或 Codex 5 小时额度剩余 < 15%）：立刻发一条
  `[quota] <me> 剩余 …，预计还能做 …`，把当前进度和下一步写清楚，别做到一半消失。
- 发现对方额度尽或长时间无响应，二选一并在消息里写明理由：
  1. **独立完成**：剩余工作量自己能扛，且不会动对方 lane；
  2. **通知用户**：需要对方能力、需要审批、或工作量超出自己额度。
- 判定「额度尽」的条件：对方明确说、或 `status` 显示长时间无活动且队列堆积、或连续 15 分钟无任何回应。

## 5. 通知用户

用户不一定盯着中转台。以下情况发邮件：

- 需要用户审批 / 回答才能继续；
- 等对方超过 15 分钟且无法自行推进；
- 额度耗尽且无法独立完成；
- 交付完成（可选，一天不超过一次汇总）。

```
node relay-cli mail --subject "[Agent] 需要你确认：<一句话>" --text "<正文>"
```

正文必须包含：谁在做什么、卡在哪、需要用户做什么、中转台链接、相关文件路径。
**邮件里不放密钥、不放超长日志。**

## 6. 禁止事项

- 未收到 `确认#<id>` 就改文件、跑构建、发消息给第三方。
- 改对方 lane 里的文件。
- 把同一条消息重复投递，或用 `send` 绕过中转台刷屏。
- 在邮件、聊天记录里粘贴 API key、cookie、token。
- 用户没批准就执行有外部副作用的操作（发送、支付、删除、改账号）。

## 7. 常用命令

```bash
node relay-cli status
node relay-cli inbox --as deepseek
node relay-cli inbox --as codex --peek
node relay-cli send --as deepseek --to codex "文本"
node relay-cli quota
node relay-cli mail --subject "[Agent] …" --text "…"
```

`status` / `inbox` / `quota` 支持 `--json`，便于机器处理。

## 8. 新会话接入清单

1. 读本 skill，确认自己是 `deepseek` 还是 `codex`。
2. `relay-cli status`，确认两边绑定与投递状态。
3. 发报到消息（含 lane 与额度）。
4. 等用户任务；收到后按 S2→S5 走，不跳步。
